# 工程案例：把运营动作留在可核查的状态边界内

下列案例将业务问题、实现取舍与仓库内的源码和测试对应起来。项目负责人统筹需求、流程、实现组织、代码审查与验证交付，研发中与 Agent 协作。

## 1. 定时计划：锁等待之后才算租约是否仍有效

**问题。** 多个调度进程可能同时看到到期计划。更隐蔽的是，一个进程在租约未到期时开始等待数据库行锁，拿到锁时租约已经过期；若沿用等待前的判断，就可能把过期采集结果挂回轮次，或多创建活动。

**实现。** [计划服务](../backend/app/services/operation_plans.py)用固定的计划→运行记录锁顺序领取轮次；续租、采集写回和阻塞写回在拿到锁并刷新记录后，按数据库 `clock_timestamp()` 重新检查状态、令牌和到期时间。网络采集不长期占用这段数据库事务。错过窗口记录为错过，默认不无限补跑；计划暂停阻止尚未创建的新活动，已开始的活动沿原状态机处理。

**取舍。** 过期或失权时停止把结果挂到计划，比“尽量完成”更保守。已经完成的真实采集可留在采集记录中供核查，但不能据此推断该计划轮次已成功创建活动。人工恢复是显式动作。

**对应断言。** [锁等待测试](../backend/tests/test_operation_plan_lease_wait.py)覆盖续租等行锁跨过截止时间、采集结果写回跨截止时间，以及阻塞原因写回跨截止时间；[计划测试](../backend/tests/test_operation_plans.py)覆盖过期领取转中断等状态行为。

## 2. 素材交付：导出固定审核版本，而不是临时拼最新文件

**问题。** 运营可能在导出过程中修改文案或媒体。如果下载时分别读取“最新文案”和“最新媒体”，交付包就可能混入不同版本；旧批准也不应覆盖新内容。

**实现。** [审核与版本服务](../backend/app/services/variant_review.py)把批准绑定到具体平台变体和版本。[导出服务](../backend/app/services/delivery.py)在短事务内检查所属用户、当前版本、有效批准及审核快照中的资产描述，随后结束事务，再读取对象并写临时 ZIP。文件按稳定编号排序，清单记录活动、平台、版本、审核时间、文件顺序及各文件 SHA-256；读取或归档失败会阻塞或清理临时文件。

**取舍。** 导出开始的批准版本是包的边界。并发编辑不会把新版内容悄悄塞进旧包；新版本需要重新审核。HEAD 预检只是资格提示，实际 GET 仍再次校验，不能把两次请求之间的状态变化忽略掉。导出成功仅代表素材交付，不代表平台发布。

**对应断言。** [交付测试](../backend/tests/test_delivery.py)覆盖跨账号拒绝、审核失效、资产缺失、小红书内容卡顺序与哈希、媒体读取期间并发编辑和临时文件清理；[审核版本测试](../backend/tests/test_review_versions.py)覆盖旧批准不带到新版本及编辑/审核竞争。

## 3. 发布任务：把“不知道是否成功”当成独立状态

**问题。** 平台请求超时或连接断开时，客户端未必知道服务端是否已经接收。把这种情况当作普通失败并自动重提，可能重复上传或重复创建内容。

**实现。** [发布任务服务](../backend/app/services/publish_jobs.py)保留幂等键、审核快照、请求标识及封面/视频/创建阶段检查点；[抖音适配器](../backend/app/integrations/publish/douyin.py)把超时、网络和无法确认的响应分类为未知。已确认的阶段可按原检查点继续，但创建请求结果不明时进入 `publish_unknown`，停止自动重新创建，并保留人工核查入口。创建受理 ID 不等于平台公开发布证明。

**取舍。** 宁可把任务停在可解释的“结果未知”，也不在缺少可靠查询能力时猜测失败。代价是需要人工查明外部结果；这比无证据重提更符合幂等边界。

**对应断言。** [HTTP 契约测试](../backend/tests/test_douyin_http.py)使用 `httpx.MockTransport` 检查请求内容、响应解析与超时分类；[阶段测试](../backend/tests/test_douyin_stages.py)覆盖已确认上传后的恢复、创建意图过期不重建、超时落入未知状态。
